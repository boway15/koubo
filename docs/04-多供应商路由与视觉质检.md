# 多供应商路由 · 视觉质检

> 本文补充 `03`，回答两个新增需求：**① 支持多供应商（即梦 / 可灵 / 海螺 h3 / kie 等中转）+ 输出多样性；② 视觉质检全部都要。**
> 先给结论：**这两件事都不是“多接几个 API”，而是两个新层——路由层和视觉质检层。**

---

## 1. 四个决策已定（本文前提）

| 项 | 结论 | 影响 |
| --- | --- | --- |
| B-roll 默认条数 | **3 条** | 成本锚点从 ¥0.2 抬到 **¥4 左右/条**，必须有预算门 |
| 供应商策略 | **多供应商 + 多样性** | 必须做路由层，不能写死单家 |
| h3（海螺 Hailuo） | **必须支持** | 第三个直连厂商，运动幅度更强 |
| 中转（kie.ai 等） | **支持** | 一套 key 访问 Veo / Sora / Hailuo / Kling |
| 视觉质检 | **全都要** | 质检从 11 项 → **17 项**（含事实保真），需接多模态 |

---

## 2. 供应商不再是“常量”，而是一张表

### 2.1 三档分层（这个分层决定了架构）

| 层级 | 代表 | 优点 | 风险 |
| --- | --- | --- | --- |
| **直连** | 即梦（Ark）、可灵、海螺（MiniMax） | 价格最低、状态可见、可提工单 | 需逐个开户、逐个看文档 |
| **中转** | kie.ai、其它聚合 | 一套 key 用 Veo/Sora/Hailuo/Kling、接入快 | **加价 20–80%**、限流不透明、可用性不受控、可能突然下线模型 |
| **自建** | FFmpeg 静态图推拉、字幕卡 | 零成本、永远可用 | 效果差 |

> 规矩：**中转只能做“扩展与备用”，不能做主通道。** 主链路必须至少有 1 条直连可用，否则某天中转改价或下线，整个生产就停。

### 2.2 数据模型：`providers` + `models` 两张表

不要用代码里的 if/else 枚举供应商，否则每加一家要改代码、改测试、发版。

```sql
create table providers (
  id text primary key,              -- jimeng | kling | hailuo | kie | local
  kind text not null,               -- direct | relay | local
  display_name text not null,
  base_url text,
  auth_kind text,                   -- bearer | jwt | header
  is_enabled bool default true,
  reliability numeric(3,2),         -- 0–1，自动统计成功率
  avg_latency_ms int,
  notes text
);

create table provider_models (
  id text primary key,              -- jimeng-seedance-i2v | kling-v2-1 | hailuo-h3-i2v | kie-veo3
  provider_id text references providers(id),
  model_ref text not null,          -- 厂商真实模型 ID / ep- 接入点
  kind text not null,               -- text2image | image2image | text2video | image2video | vision | text
  capabilities jsonb not null,      -- { ratios, maxDurationSec, seed, firstFrame, lastFrame, audio }
  unit_price numeric(10,4),
  unit_name text,                   -- per_second | per_call | per_1k_tokens | per_image
  quality_tier int,                 -- 1=快省 2=均衡 3=高质量
  is_enabled bool default true,
  deprecated_at timestamptz
);
```

关键：`capabilities` 是 **JSON**，所以新增一家供应商只是插两行数据，不改代码。这是“支持多样性”的工程前提。

### 2.3 能力协商：不支持的参数，路由前就拦掉

每家能接受的参数不一样，硬传就报错。所以路由阶段先做能力过滤：

| 能力位 | 即梦 | 可灵 | 海螺 h3 | kie（视模型） |
| --- | --- | --- | --- | --- |
| 首帧驱动（i2v） | ✅ | ✅ | ✅ | ✅ |
| 尾帧 / 首尾帧 | ⚠️ 视模型 | ⚠️ 视模型 | ⚠️ 视模型 | 视上游 |
| 固定 seed | ✅ | ✅ | 部分 | 不可靠 |
| 单段时长 | 5 / 10 | 5 / 10 | 5 / 6 / 10 | 5 / 8 / 10 |
| 原生音频 | ❌ | 部分 | ✅（部分型号） | 视上游 |
| 9:16 竖屏 | ✅ | ✅ | ✅ | 视上游 |

> 这张表**在数据库里**，不在代码里。跑一个探测脚本即可自动填充（每个能力发一次最便宜的请求，看返回）。

## 3. 路由层：四个策略，可按镜头覆盖

### 3.1 策略枚举

```ts
type RoutePolicy =
  | { kind: 'single'; modelId: string }                    // 指定模型
  | { kind: 'cheapest'; minTier?: number }                 // 同能力里最便宜
  | { kind: 'quality'; minTier?: number }                  // 同能力里质量最高
  | { kind: 'diverse'; pool: string[] }                    // 多样性：每个镜头换着用
  | { kind: 'fallback'; chain: string[] }                  // 显式降级链
```

### 3.2 “多样性”具体怎么实现

用户说的“支持多样性”在工程上有两种含义，两种都要支持：

**① 视觉多样性（推荐默认）**：同一单里的 3 个 B-roll 分给 3 家不同厂商，避免“一眼 AI 同款质感”。

```
shot 02 → 即梦（产品细节，重一致性）
shot 04 → 可灵（使用动作，重运镜）
shot 06 → 海螺 h3（氛围/旋转，运动幅度大）
```

**② 备选多样性（人工挑选）**：同一个镜头让 2–3 家各生成一遍，并排给客户/编导挑。成本 ×N，但成交率明显更高。

```
一个镜头 → 即梦 / 可灵 / h3 各一版 → 九宫格挑选 → 选中的入素材库
```

实现上都是 `route(diverse, pool)`，区别只是 `sampleCount`（1 或 3）。

### 3.3 路由必须写的三条排序因子

```
候选 = 能力匹配 ∧ 已启用 ∧ 未弃用
排序 = 健康分(成功率) × 0.5 + 质量档 × 0.3 + 成本倒数 × 0.2
```

健康分是**滑动窗口自动统计**的（近 50 次成功率）。某家中转连续失败会自动跌出候选，不需要人工介入。

### 3.4 中转的特殊处理（kie 这类）

中转不是“另一家厂商”，是**一个可能随时变的黑盒**，所以单独对待：

| 问题 | 处理 |
| --- | --- |
| 加价不透明 | `unit_price` 手工维护 + 每月对账一次；成本面板单独标“中转”标签 |
| 模型名会变 | `model_ref` 存中转侧名称，与上游解耦；变更只改数据 |
| 状态字段不统一 | 适配器内部归一化为 `pending/running/succeeded/failed` |
| 拿不到 task 明细 | 失败只归因为 `relay_unknown`，不盲目重试（可能已扣费） |
| 可能突然下线 | `is_enabled` 一键关；主链路不依赖它 |
| 合规主体不清 | 对外交付的成片若用过中转，**内部留记录**，便于追溯 |

> 一条硬规则：**中转失败时不要自动重试超过 1 次。** 因为不透明，重试可能重复扣费且无法举证。

## 4. 海螺 h3 接入要点

| 项 | 说明 |
| --- | --- |
| 平台 | MiniMax 开放平台（需 `group_id` + API Key） |
| 形态 | 异步：创建任务 → 轮询 → 拿文件 URL |
| 优势 | 运动幅度、镜头语言强；部分型号**原生带音频** |
| 对我们 | 适合做“氛围镜头 / 旋转展示”，不适合做产品细节特写（一致性不如图生视频） |
| 注意 | 模型 ID 版本迭代快，务必用 `provider_models` 表管理，别写进代码 |

如果我们要用它的原生音频，那是额外的能力：**B-roll 自带环境音**，可以省掉一层音效匹配。但要注意与配音的音量平衡（人声时 ducking）。

## 5. 统一错误码（跨供应商的重试/降级依据）

不同厂商错误码完全不同，必须先归一化，否则降级逻辑写不出来：

```ts
type NormalizedError =
  | { code: 'rate_limited';     retryable: true  }
  | { code: 'server_error';     retryable: true  }
  | { code: 'timeout';          retryable: true  }
  | { code: 'content_blocked';  retryable: false }   // 换 prompt 或降级
  | { code: 'invalid_param';    retryable: false }   // 我们的 bug
  | { code: 'insufficient_fund';retryable: false }   // 全局熔断
  | { code: 'model_unavailable';retryable: false }   // 换模型
  | { code: 'relay_unknown';    retryable: false }   // 不重试
```

降级链根据 `code` 走不同分支：

```
content_blocked → 改写 prompt 重试 1 次 → 仍拦截 → 换另一家 → 仍拦截 → 静态图
model_unavailable → 直接换另一家（不重试同一家）
insufficient_fund → 熔断全部付费生成，转静态图 + 报警
relay_unknown → 不重试，人工确认
```

## 6. 视觉质检：11 → 17 项

### 6.1 为什么必须加

DeepSeek 不看图，所以原方案里“封面可读”“画面合规”只能算近似值。既然要做商业交付，**这两类必须真看图**。

### 6.2 新增项

**12–14（画面类）**

| # | 检查项 | 方法 | 失败后果 |
| --- | --- | --- | --- |
| 12 | 画面内容合规 | 多模态：抽 3–5 帧 + 封面图，检查禁用元素（竞品 logo、真人明星、违规场景、裸露、暴力）；**另含镜头间色调偏差** | 阻断 |
| 13 | 封面观感与可读 | 多模态 + 像素规则双轨：模型判“缩略图下是否抓眼”，规则算字号占宽、对比度、重要元素是否被裁 | 警告（可一键换封面） |
| 14 | 字幕与画面同步 | 规则：字幕时间戳 vs 音频能量包络，偏差 > 300ms 报警；另检查字幕是否被遮挡（安全区） | 警告 |

**15–17（知识类特有，保真类）**

| # | 检查项 | 方法 | 失败后果 |
| --- | --- | --- | --- |
| 15 | 数值与术语保真 | 抽取改写稿所有数字/专有名词，逐个回原文核对；未在原文出现的**数字**直接 fail | 阻断 |
| 16 | 事实可溯源 | 每个论断需能对应原文某句；无出处的断言标 warn | 警告 |
| 17 | 无自行补充 | 对比原文与改写稿的“信息点集合”，新增信息点且无来源 → fail | 阻断 |

> 第 17 项是知识类的命门：模型“聪明地补了一条论据”，在带货里是加分，在知识领域是事故。详见 `06-业务适配分析.md` 第 3.3 节。

### 6.3 多模态选型

| 方案 | 优点 | 说明 |
| --- | --- | --- |
| **豆包视觉（Ark，doubao-vision）** | 与即梦同一个 key、同一个计费账户 | **首选**，省一套凭据 |
| 通义 Qwen-VL | 中文场景理解好 | 备选 |
| 智谱 GLM-4V | 便宜 | 备选 |

**不要用 DeepSeek 做视觉**——它没有视觉接口。这是架构限制，不是选型偏好。

### 6.4 抽帧策略（决定成本与准确率）

```
每支成片抽 5 帧：0s（钩子）、25%、50%、75%、末帧（CTA）
封面单独 1 张（全分辨率）
一单合计 6 张图 → 一次多模态调用（多图输入）
```

成本量级：**¥0.01–0.05 / 单**。相比视频生成可以忽略，但**必须走同一套预算闸门**，否则单子多了会累积。

### 6.5 质检结论怎么落

```json
{
  "check_id": 12,
  "verdict": "fail",
  "evidence": { "frames": ["t=00:14"], "finding": "第 14 秒画面出现竞品杯体", "confidence": 0.82 },
  "fix_suggestion": "替换 shot 04 或重新生成",
  "model": "doubao-vision",
  "cost": 0.02
}
```

**`evidence` 必须带具体帧与置信度**，否则人工无法复核，质检就变成了“模型说不行”。置信度 < 0.7 的建议降为 `warn` 而不是 `fail`——避免误阻断。

## 7. 成本重算（B-roll = 3 + 视觉质检）

| 项 | 量 | 单价量级 | 小计 |
| --- | --- | --- | --- |
| DeepSeek（拆解+改写+文案+文本质检） | ~8k tokens | — | ¥0.05–0.15 |
| TTS | ~150 字 | — | ¥0.03–0.10 |
| **B-roll × 3**（直连 5s） | 3 条 | ¥0.8–1.5/条 | **¥2.4–4.5** |
| B-roll × 3（走中转） | 3 条 | ¥1.5–3.0/条 | ¥4.5–9.0 |
| 视觉质检 | 6 张图 | — | ¥0.01–0.05 |
| 渲染 | 30s | — | ¥0.10 |
| **合计（直连）** | | | **¥2.6–4.9** |

结论：**B-roll 成为绝对成本大头（>80%）**。所以：

1. 预算闸门必须做在**镜头级**，不是项目级才算。
2. 客户改稿时，**只重生变动的镜头**，不要整片重跑（这是省钱的唯一办法）。
3. 中转只用于“扩展”，价格敏感的单子强制走直连。

## 8. 落地顺序（增量部分）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| R1 | `providers` / `provider_models` 两表 + 能力探测脚本 | 新增一家供应商只需插数据，不改代码 |
| R2 | 路由层 + 健康分统计 + 多样性策略 | 同一单 3 镜分给 3 家；某家禁用后自动换 |
| R3 | 海螺 h3 适配器 | 同首帧可与即梦/可灵对比 |
| R4 | 中转适配器（kie） | 中转失败不重试、不阻塞主链路 |
| R5 | 多模态视觉质检（12–17 项） | 能指出“第 14 秒有竞品”，带置信度 |
| R6 | 镜头级预算闸门 + 单镜重生成 | 改一镜只花一镜的钱 |

## 9. 两个新风险（必须写进风险表）

| 风险 | 后果 | 缓解 |
| --- | --- | --- |
| **成本失控**：默认 3 条 B-roll + 客户反复改 | 单条成本可能超 ¥20 | 镜头级预算 + 只重生变动镜头 + 单项目硬上限 |
| **中转依赖**：kie 改价/下线/限流 | 生产停摆，且无法追责 | 主链路至少 1 条直连；中转仅扩展；`is_enabled` 一键关 |

还有一个隐藏风险：**多样性会导致视觉不统一**。3 个镜头来自 3 家，色调和质感可能差很多。缓解：所有 B-roll 生成后过一遍**统一调色**（FFmpeg LUT），并限制同单只用同一套 prompt 风格前缀。

## 10. 已锁定的两个决策

| 项 | 结论 |
| --- | --- |
| 多样性默认 | **分给不同厂商**（每镜一家，`sampleCount = 1`） |
| 中转标注 | **可以标注**，写在 `manifest.json` 与 `publish-notes.md`，不上画面 |

配套三道约束（防止“三家色调不统一”）：

1. 同一单共用一套 prompt 风格前缀；
2. 所有 B-roll 生成后过一遍统一 LUT；
3. 质检项 12 增一条“镜头间色调偏差 > 阈值 → warn”。

详见 `05-PC客户端与技术演进.md` 第 1 节。
