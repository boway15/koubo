# V1 范围收敛 · 国内模型选型 · SaaS 预留 · 交付端

> 基于四条新确认：①工作室先用、后期 SaaS 化、需支持输出给客户；②本地 Docker；③模型国内优先；④V1 必须做「视频上传 + ASR」；⑤暂不做矩阵批量。
> 本文是对 `01-系统分析与技术方案.md` 的收敛与补充，冲突时以本文为准。

---

## 1. 五个决策的工程含义

| 决策 | 真正的工程含义 | 不该做的事 |
| --- | --- | --- |
| 工作室先用、后期 SaaS | 不是“先单机再重构”，而是**一开始就带 `org_id` 和存储前缀**，只是不开配额、计费、注册 | 不要写死全局单例、不要把文件存本地磁盘路径 |
| 支持输出客户端（交付端） | 多一个**客户审阅面**：免登录签名链接、逐句批注、通过/驳回回写 | 不要让客户进后台，不要让客户看到 AI 提示词与成本 |
| 本地 Docker | 一把 `docker compose up`，含 ffmpeg、ASR、DB、对象存储 | 不要依赖云托管服务才能跑 |
| 模型国内优先 | 选型按“可用性 + 字级时间戳 + 合规”排序，不按跑分 | 不要为了效果引海外 API 进主链路（跨境合规 + 网络不稳） |
| V1 = 上传视频 + ASR | ASR 是**必须路径**，不是备选；链接解析延后 | 不要在 V1 内做抖音抓取，它是维护黑洞 |

一句话：**V1 的成败不在“能不能生成”，而在“客户能不能一次性通过”。**

## 2. V1 范围（冻结）

### 2.1 进料：三条入口，一条主路

| 入口 | V1 | 说明 |
| --- | --- | --- |
| 上传视频 + ASR | ✅ **主路径** | mp4/mov ≤ 200MB ≤ 5min；抽音轨 →（可选）人声分离 → ASR 带时间戳 |
| 粘贴文案 | ✅ | 零成本兜底，永远可用 |
| 只给主题 | ✅ | 跳过拆解，直接生成大纲 |
| 抖音链接解析 | ❌ 延后 V1.5 | 留接口与 UI 入口（置灰/开关），不写抓取逻辑 |

> ASR 必须输出**词/字级时间戳**，因为下游字幕和分镜对齐都靠它。没有时间戳的 ASR 等于没有。

### 2.2 明确不做（V1）

- 矩阵批量生产（一次 1 条，队列串行即可）
- 数字人（留 driver 接口，UI 置灰并标“增强项”）
- 自动发布 / 账号托管 / 多平台分发
- 团队协作（成员、角色、审批流）→ 但**数据表预留**
- 模板市场、素材库检索、A/B 测试

### 2.3 V1 必须交付的能力清单

```
① 上传视频 → ASR（带时间戳）→ 结构化拆解
② 差异化改写（5 项量化阈值 + 自动重写≤2 次）
③ TTS 配音（字级时间戳）→ SRT 字幕
④ 图片 + 模板剪辑（FFmpeg）→ 1080×1920 成片
⑤ 封面生成（HTML 模板截图，主标题 ≤ 8 字）
⑥ 三平台发布文案
⑦ 17 项质检（含多模态画面 + 事实保真）+ 强制放行留痕
⑧ 导出固定 8 件产物（zip）
⑨ 客户交付页（免登录签名链接 + 通过/驳回回写）
⑩ 成本面板（按项目归因）
```

## 3. 国内模型选型

### 3.1 选择原则

1. **可商用授权**优先于跑分。
2. **字级时间戳是硬门槛**（TTS / ASR）。
3. 每个能力位至少留 **1 个可切换的备选**（provider adapter），主备不同厂商，避免单点。
4. 能在本地跑的（ASR、embedding、渲染）**优先本地**：免费、可离线、隐私好、不受限流。
5. 云端只用在“本地做不好”的三处：**LLM 改写、TTS 音色、数字人**。

### 3.2 能力位矩阵

| 能力位 | 首选（本地） | 云端主力 | 云端备选 | 关键验收点 |
| --- | --- | --- | --- | --- |
| **ASR** | `faster-whisper large-v3`（GPU 可选，CPU 可用 int8） | 阿里 Paraformer（带时间戳） | 讯飞、腾讯 | 中文口播 + BGM 下字准率；**必须回词级时间戳** |
| **人声分离** | Demucs v4（`htdemucs`） | — | UVR5 | 有 BGM 时必须过一遍，ASR 字准率明显提升 |
| **Embedding（差异打分）** | BGE-M3（ONNX/CPU 可跑） | 阿里 text-embedding-v3 | — | 逐句余弦，用来抓“近义搬运” |
| **LLM（改写/拆解/质检/文案）** | — | DeepSeek-V3 系（性价比） | 通义千问 Qwen-Plus/Max、豆包、GLM、Kimi | 严格 JSON 输出、中文口语感、单价 |
| **TTS** | — | 火山引擎语音合成（大模型音色） | 阿里云、讯飞、MiniMax | **必须返回字/词级时间戳**；多音字、数字读法可词典干预 |
| **数字人（V2）** | — | 火山（照片说话） | 硅基智能、腾讯智影 | 口型质量、排队时长、失败退款 |
| **封面/剪辑** | FFmpeg + libass；封面用 Playwright 截图 | — | Remotion（二期） | 无 GPU 也要能在 1–2 分钟内出片 |

> LLM 分工建议：**改写**用强模型（质量决定客户是否通过），**拆解/文案/质检打分**用便宜模型。按项目记录 token，成本差异会很明显。

### 3.3 选型上必须实测的三件事

在写业务代码之前，先花半天做三个 spike，不然会返工：

1. **TTS 时间戳精度**：合成一句 20 字中文，取回时间戳，与音频对齐误差是否 < 80ms。
2. **ASR 在 BGM 下的字准率**：拿 3 条真实口播视频，对比“直接 ASR”与“人声分离后 ASR”的字错数。
3. **改写阈值在真实语料上的分布**：拿 10 对“原片 vs 改写”，看 4-gram 与句向量的分布，再定阈值（0.20 / 0.85 是起点，不是圣旨）。

### 3.4 合规提醒（国内 SaaS 化时必读）

- 面向公众提供服务时，生成式 AI 需按现行规定完成**备案/登记**；内部工作室自用不涉及。
- 深度合成内容需**显式标识**（画面角标）与**隐式标识**（文件元数据），已在渲染层内置。
- 客户素材需授权声明；BGM 只用可商用曲库。
- 正式上线前按当时最新法规核对，本文不作为法律意见。

## 4. 数据模型：SaaS-ready 但不提前复杂化

### 4.1 现在就要埋的三根钉子

```sql
-- 1) 所有业务表带 org_id（V1 只有 1 行 org）
alter table projects add column org_id uuid not null default '...';

-- 2) 存储 key 一律带租户前缀，禁止裸路径
--    s3://koubo/{org_id}/{project_id}/{artifact_id}.mp4

-- 3) 供应商凭据走表，不写环境变量硬编码
create table provider_credentials (
  org_id uuid, provider text, kind text, secret_ref text, is_default bool
);
```

### 4.2 现在不要做的

- 配额表、计费表、订阅表（等有第二个客户再建）
- Postgres RLS（先用应用层 `where org_id = ?`，RLS 留作 SaaS 化时的加固项）
- 独立部署单元、按租户拆库

> 判据：**加一个租户只需插一行 org、换一组 key**，不需要改代码——这个标准就够了。

### 4.3 SaaS 化时要补的东西（提前知道，避免踩坑）

| 项 | 改造点 |
| --- | --- |
| 隔离 | 应用层过滤 → Postgres RLS + 存储策略 |
| 配额 | 新增 `org_quotas`，在入队前拦截（不要在任务里失败） |
| 计费 | `provider_calls` 已有单价与用量，直接聚合即可出账 |
| 并发 | 队列按 org 分优先级，防止单租户占满渲染池 |
| 注册/登录 | 引入 IdP（邮箱验证码 + 邀请制起步最省事） |

## 5. 交付端（输出给客户）

这是工作室场景里**最被低估的一环**：不是交付文件，是交付“一次确认”。

### 5.1 形态

```
POST /api/deliveries            生成交付（绑定项目某个版本快照）
GET  /d/:token                  客户免登录页面
POST /api/deliveries/:token/decision   { action: approve | request_changes, items[] }
```

- 链接签名 + 有效期（默认 7 天）+ 可撤销
- **绑定版本快照**：客户看的是 v2，工作室后续改到 v4 不会悄悄替换（重新发一版新链接）
- 客户只能看：成片、封面、字幕、发布文案；看不到提示词、成本、其他项目

### 5.2 客户侧能做的两件事

1. **逐句批注**：在字幕时间轴上点某一句留意见（带时间码），避免“第 30 秒那里不太好”这种沟通。
2. **通过 / 需修改**：通过后项目状态 → `approved`，可直接导出；需修改会把批注聚合成一张任务清单回到工作台。

### 5.3 回写闭环

```
客户批注 ──▶ 工作台「客户意见」面板（带时间码，点击跳到对应句子）
        ──▶ 命中哪一步？（改稿 / 换镜头 / 改封面 / 改文案）
        ──▶ 人工确认后触发单步重跑（不自动）
        ──▶ 重新生成交付链接（版本 +1）
```

> 这条闭环是留住工作室客户的关键：**客户的每一次“再改一下”都能被结构化成一条可追踪的记录**，而不是微信里的一段语音。

### 5.4 数据模型

```sql
create table deliveries (
  id uuid primary key,
  org_id uuid not null,
  project_id uuid not null,
  token text unique not null,        -- 32 字节随机，不可猜
  snapshot_json jsonb not null,      -- 锁定的 artifact 版本清单
  expires_at timestamptz not null,
  revoked_at timestamptz,
  decided_at timestamptz,
  decision text                      -- approve | request_changes
);

create table client_comments (
  id uuid primary key,
  delivery_id uuid not null,
  cue_index int,                     -- 对应字幕第几句
  timecode_ms int,
  author_name text,
  body text not null,
  resolved_step text,                -- rewrite | render | copy（人工确认后填）
  created_at timestamptz default now()
);
```

两个安全细节，容易被忘：

1. `snapshot_json` 必须存**产物 ID 列表**，而不是“最新”指针。否则客户看到的内容会随工作室修改而变。
2. 客户页的媒体链接用**短时签名 URL**（例如 10 分钟），不要直接把 MinIO 公共地址泄露出去。

### 5.5 交互原型

已在 `prototype/deliver.html` 做出可点击版本（桌面与手机宽度都能看），工作室侧的回写面板在第 8 步「客户交付」卡片。

## 6. 修订后的里程碑

| 阶段 | 内容 | 工期 | 验收 |
| --- | --- | --- | --- |
| **S0 · Spike** | TTS 时间戳 / ASR 字准率 / 改写阈值三项实测 | 0.5–1 天 | 三项均有数据结论 |
| **M0 · 骨架** | 三张核心表 + 产物 DAG + stale + 队列 + SSE | 3–5 天 | 改一句文案，只下游变灰，单步重跑不重复扣费 |
| **M1 · 主链路** | 上传视频 + ASR → 改写 → TTS/字幕 → 图片模板合成 → 封面 → 导出 8 件 | 1.5–2 周 | 一单从上传到拿到 zip 全自动，含人工确认点 |
| **M2 · 质量与交付端** | 17 项质检（含多模态与事实保真）、三平台文案、成本面板、**客户交付页** | 1 周 | 客户能免登录审阅并回写通过/驳回 |
| **M3 · 可选增强** | 数字人 driver、链接解析、模板库 | 按需 | 不改主链路即可插拔 |

总计到「能交付第一个真实客户」约 **3–4 周**（单人全职）。

## 7. 风险变化（相比 01 文档）

| 风险 | 变化 | 缓解 |
| --- | --- | --- |
| 链接解析维护 | **↓ 大幅下降**（V1 不做） | 只留 UI 入口与接口占位 |
| ASR 成为主路径 | **↑ 上升**（必须稳定） | 本地 faster-whisper + 人声分离；失败可重跑单段 |
| TTS 时间戳不达标 | **↑ 上升**（供应商硬门槛） | 选型前先 spike；不达标则强制分句 + 比例内插兜底 |
| 客户反复改 | **↑ 新增**（交付端引入的循环） | 逐句批注 + 意见聚合 + 单步重跑，避免整片重做 |
| 后期 SaaS 化返工 | **↓ 下降**（已埋 org_id 与存储前缀） | 按 4.3 清单推进，不要提前做 |
| 国内模型波动 | 中 | 每个能力位主备不同厂商，adapter 可切换 |

## 8. 还需要你拍板的三个小问题

1. **客户交付页要不要带你的品牌**（logo / 主色 / 落款）？要做的话 V1 就要引入 `brand_kits` 表。
2. **交付链接默认有效期**：7 天 / 30 天 / 长期？
3. **ASR 跑在哪**：纯 CPU（慢但零配置）还是给 Docker 开 GPU（快 5–10 倍）？这决定 compose 的写法。
