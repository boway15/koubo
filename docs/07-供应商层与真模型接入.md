# 供应商层与真模型接入

> 这份文档对应 M0 的第 1 步落地：把 `src/steps/` 里的确定性实现换成真实模型调用，同时保证**没有 key 也能跑**。

---

## 1. 分层：谁该知道什么

```
steps/            业务步骤（intake / rewrite / produce / qc …）
  ↓ 只依赖接口
agents/           单个能力的编排（rewrite 校验+修复、voice 时间戳否决）
  ↓ 只依赖接口
providers/        供应商适配（DeepSeek / TTS / 未来的即梦可灵）+ 路由 + 错误码
  ↓
core/             DAG / hash / 质检 / 时间线 —— 完全不认识任何厂商
```

三条分层规矩，违反任意一条都会在接第二家时返工：

1. **`core/` 里不出现厂商名**。质检只认 `artifact.kind`，不认 `deepseek`。
2. **`agents/` 里不出现 `if (provider === 'xx')`**。差异全部落在注册表的 `capabilities`。
3. **`steps/` 里不写重试**。重试、降级、健康分、成本归因都在 `dispatch()`。

---

## 2. 注册表：加一家 = 加一行

生产环境是 `db/schema.sql` 的 `providers` + `provider_models`；M0 用 `src/providers/registry.js` 里的同形状种子。

```js
{
  id: "volc-tts",
  provider_id: "volc_tts",
  model_ref: "volc_tts_zh_female",
  kind: "tts",
  capabilities: { zh: true, word_timestamps: true, max_chars: 300 },
  unit_price: 0.003, unit_name: "1k_chars", quality_tier: 3
}
```

**能力写数据，不写代码。** 路由用 `require: { word_timestamps: true }` 过滤，而不是靠模型名判断。

---

## 3. 路由：五个策略 + 一条排序公式

```js
route({ kind: "video", policy: { kind: "diverse" } })
// → 有序候选列表，调用方照着试，第一个失败自动落下一个
```

| 策略 | 用途 |
| --- | --- |
| `single` | 指定模型（客户指定/复现某条片子） |
| `cheapest` | 草稿阶段压成本，可设 `minTier` 保底质量 |
| `quality` | 交付版本 |
| `diverse` | 3 个 B-roll 分给 3 家（默认），`pickDiverse` 保证不重复 |
| `fallback` | 显式降级链，链外候选仍接在后面 |

排序：`健康分 × 0.5 + 质量档 × 0.3 + 成本倒数 × 0.2`

健康分是近 50 次滑动窗口成功率，尾部连续失败额外扣分（最多 −0.6）。没跑过的新供应商给 0.95，**不惩罚新加入者**。

---

## 4. 统一错误码：降级链的唯一依据

| code | retryable | 处置 |
| --- | --- | --- |
| `rate_limited` | ✅ | 退避重试 1 次 |
| `server_error` | ✅ | 重试 1 次 |
| `timeout` | ✅ | 重试 1 次 |
| `content_blocked` | ❌ | 改 prompt / 换家 / 静态图 |
| `invalid_param` | ❌ | 我们的 bug，告警 |
| `insufficient_fund` | ❌ | 熔断全部付费生成 |
| `model_unavailable` | ❌ | 直接换家 |
| `relay_unknown` | ❌ | 不重试（可能已扣费），人工确认 |

`normalizeError` 的判定顺序是 **status → 文案 → 中转兜底**。为什么文案要压过 status：余额不足经常也返回 400，只看 status 会当成参数错误，然后无限重试。

## 5. 两条真实契约

### 文本（DeepSeek）

```
POST {base}/chat/completions
{ model, messages:[{role:system},{role:user}], temperature, response_format:{type:"json_object"} }
→ { choices:[{message:{content}}], usage:{total_tokens,prompt_cache_hit_tokens} }
```

`SYSTEM` 一字不改，前缀缓存才命中。运行期变量（预算、平台、原文）全部走 user 消息。

### 配音（TTS）

```
POST {base}/tts
{ text, voice, model, format:"wav", word_timestamps:true }
→ { audio_url, dur_ms, words:[{text,start_ms,end_ms}] }
```

**字级时间戳是一票否决项**，判定条件三条同时满足：

- `words` 非空
- 单调且不重叠
- 覆盖率 `Σ(end-start)/dur_ms ≥ 0.8`

任何一条不满足 → `model_unavailable` → 换下一家；全都换完 → 估算兜底 + `timestampSource: "estimated"`。

## 6. 降级矩阵（这是这套设计最该被验收的部分）

| 环节 | 有凭证 | 无凭证 | 模型输出不合格 |
| --- | --- | --- | --- |
| 改写 | DeepSeek | 本地模板 | 修复 1 次 → 仍不合格则本地模板 |
| 配音 | 真 TTS（字级时间戳） | 字数估算 | 换供应商 → 全失败则估算 |
| 第 14 项质检 | 覆盖率 ≥ 80% 才 pass | 强制 warn | 覆盖率不足直接 fail |
| 交付 `provenance` | `engine: deepseek` | `degraded: no_api_key` | `degraded: <错误码>` |

**铁律：降级必须留痕，不许假装成功。** 估算时间轴永远拿不到 `pass`，因为"对上了"只是两边都按字数算的巧合。

## 7. 实现时才暴露的三个坑

### ① 自读自写的步骤会把自己判过期

`produce` 读 `subtitle`，又用 TTS 时间戳重写 `subtitle`。`putArtifact` 写完立刻 `markDownstreamStale("subtitle")`，而 `produce` 自己就读 `subtitle`，于是刚跑完就被标 stale —— 每次重跑都会再调一次 TTS，缓存完全失效。

修法：`putArtifact(project, artifact, { emittedBy })`，**排除产出者自身**。这不是特判，任何"读-改-写同一产物"的步骤都适用。

### ② 字幕漂移被误判成"超出音频结尾"

字幕条 start 落在下一段开头（如 31560ms），但查找用的是 `find()` 返回第一个匹配的分段——上一段的 `start+dur+gap+容差` 恰好覆盖到它，于是 end 被拿去和上一段的结尾比，报出假漂移。

修法：取**最后一个 `startMs ≤ cue.startMs` 的分段**，不是第一个匹配的。

### ③ 孤立标点条

按 20 字硬切时会把句号切到下一屏，观众看到只闪一个「。」的字幕。

修法：构建完做一次后处理，纯标点的条并回上一条。

## 8. 接一家新 TTS 的三步

1. 往 `provider_models` 插一行，`capabilities.word_timestamps = true`，填 `unit_price`。
2. 适配器只要返回契约里的三个字段（`audio_url` / `dur_ms` / `words`），协议不同就在 `createHttpTtsClient` 外面包一层。
3. 跑 `node --test app/test/providers.test.js`。如果覆盖率校验没拦住，说明它给的时间戳是假的。
