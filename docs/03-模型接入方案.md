# 模型接入方案：即梦 / 可灵 / DeepSeek

> 补充 `01`、`02` 两份文档。本文回答三个问题：**这三个模型各自接在哪一步**、**怎么接才能不卡死**、**怎么不被视频模型烧穿预算**。
>
> ⚠️ 接口路径、模型 ID、价格变动频繁，本文给出的是**结构与契约**；具体 ID 与单价请在开工前到控制台核对一次（见第 10 节核对清单）。配套可跑的最小验证见 `spikes/`。

---

## 1. 先把三个模型放到正确的位置

这是最容易做错的一步：以为“接了大模型就能全自动出片”。实际上它们的职责边界很硬：

| 模型 | 接在哪一步 | 做什么 | **不做什么** |
| --- | --- | --- | --- |
| **DeepSeek** | 第 2/3/7/8 步 | 拆解、差异化改写、发布文案、质检打分 | ❌ 不看图（纯文本接口）→ 画面质检得另接多模态 |
| **即梦（Seedream / Seedance）** | 第 5、6 步 | 生成/改写产品图、生成 B-roll 动态镜头 | ❌ 不做口播口型（做不到口型同步） |
| **可灵（Kling）** | 第 5、6 步 | 图生视频（首帧驱动）、空镜、产品旋转镜头 | ❌ 同上，且**单段只有 5s/10s** |
| **海螺（Hailuo / h 系列）** | 第 5、6 步 | 图生视频，镜头语言与运动幅度更强 | ❌ 同上，无口型 |
| **中转聚合（kie.ai 等）** | 第 5、6 步 | 一套 key 访问 Veo / Sora / Hailuo / Kling / Seedance | ❌ **不能做唯一通道**（加价、限流、可用性不可控） |
| **多模态视觉模型** | 第 8 步 | 画面内容与封面观感质检 | ❌ 不做精确定量（对比度、字数用规则算） |

### 1.1 一条必须提前说清的结论

> **视频模型不能承担口播主体。**

口播视频的核心是“人在说话”，而即梦/可灵生成的是没有口型的动态画面。让它们生成 30 秒“人在介绍榨汁杯”，会得到：口型不对、文字乱变、手部畸变。

所以正确的分工是：

```
口播主体（人说话）  → 配音 + 字幕 + 图片   或   数字人（V2）
动态补充（B-roll）  → 即梦 / 可灵 生成 5s 镜头，插在空镜位
产品图美化/改造     → 即梦（Seedream）图生图
```

**结果：视频模型是“素材增强”，不是“主体生产”。** 这个定位决定了成本可控（只生成 1–3 个镜头，不是整片）。

## 2. 统一接入层：三个模型共用一套契约

### 2.1 为什么要抽象：两个是异步任务，一个是流式同步

| 模型 | 调用形态 | 单次耗时 | 关键差异 |
| --- | --- | --- | --- |
| DeepSeek | 同步（流式可选） | 3–30s | 失败可立即重试 |
| 即梦 | **异步任务 + 轮询** | 30s–5min | 需 submit→poll→download |
| 可灵 | **异步任务 + 轮询** | 1–10min | 同上，且 JWT 鉴权 |

如果业务代码直接调 HTTP，将来换供应商要改全链路。所以所有调用都必须过一层适配器。

### 2.2 接口契约

```ts
// ---------- 文本 ----------
type TextProvider = {
  complete(req: {
    model: string                 // deepseek-chat | deepseek-reasoner
    system: string                // 固定前缀（命中缓存的关键）
    user: string
    json?: object                 // 期望的 JSON Schema（用于校验）
    temperature?: number
    maxTokens?: number
  }): Promise<{ text: string; json?: unknown; usage: Usage }>
}

// ---------- 图片/视频（异步任务） ----------
type MediaProvider = {
  submit(req: MediaRequest): Promise<{ taskId: string }>
  poll(taskId: string): Promise<{
    status: 'pending' | 'running' | 'succeeded' | 'failed'
    outputs?: Array<{ url: string; kind: 'image' | 'video'; durationMs?: number }>
    error?: { code: string; message: string; retryable: boolean }
  }>
  estimateCost(req: MediaRequest): Cost   // 必须在提交前算，用于预算熔断
  capabilities: {
    text2image: boolean
    image2image: boolean
    text2video: boolean
    image2video: boolean
    maxDurationSec: number              // 即梦/可灵：5 或 10
    ratios: string[]                    // 9:16 | 16:9 | 1:1
  }
}
```

### 2.3 一个 `media_tasks` 表把异步问题关在笼子里

```sql
create table media_tasks (
  id uuid primary key,
  org_id uuid not null,
  project_id uuid not null,
  shot_id uuid,                      -- 对应分镜（可空：封面、产品图）
  provider text not null,            -- jimeng | kling
  model text not null,
  kind text not null,                -- image | video
  request_json jsonb not null,       -- 完整请求快照（可复现）
  prompt text not null,
  prompt_version text not null,      -- 提示词模板版本
  idempotency_key text unique,       -- hash(request_json) 防重复提交
  provider_task_id text,
  status text not null,              -- queued|running|succeeded|failed|canceled
  attempt int default 1,
  cost_estimate numeric(10,4),
  cost_actual numeric(10,4),
  output_artifact_id uuid,           -- 落到 artifacts 表
  error_json jsonb,
  submitted_at timestamptz,
  finished_at timestamptz
);
```

四条硬规则：

1. **提交前写库**（状态 `queued`），再调 API。进程崩了不会丢任务。
2. **`idempotency_key` 唯一**：同一请求重复点“重生成”不会扣两次钱。
3. **轮询用独立的 worker**，指数退避：3s → 5s → 8s → … 上限 15s，超时 15 分钟判失败。
4. **产物 URL 必须立刻下载进 MinIO**。即梦与可灵返回的都是临时地址（几小时到几十天不等），不下载就等于丢数据。

> 第 4 条是这类接入最常踩的坑：跑通当天一切正常，第二天要重新渲染时发现 URL 全 403。

### 2.4 失败处理矩阵

| 情况 | 判定 | 动作 |
| --- | --- | --- |
| HTTP 429 / 限流 | 可重试 | 退避重试 3 次 |
| 5xx | 可重试 | 退避重试 3 次 |
| 内容审核拦截（合规） | **不可重试** | 换措辞重写 prompt 一次；仍拦截则**降级到图片路线**并告知 |
| 超时（>15min） | 不可重试 | 标记失败，保留 task_id 供人工到控制台查 |
| 余额/配额不足 | 不可重试 | 全局**熔断**，阻止后续提交，报警 |
| 生成成功但画面不可用 | 人工判断 | 保留结果，不自动重试（省成本） |

## 3. DeepSeek 接入

### 3.1 基本参数

```
Base URL   https://api.deepseek.com        （OpenAI 兼容，可直接用 openai sdk）
鉴权        Authorization: Bearer $DEEPSEEK_API_KEY
模型        deepseek-chat        （V3 系，通用 + JSON）
            deepseek-reasoner    （R1 系，强推理，但不适合结构化输出）
```

### 3.2 模型分工（直接影响质量与成本）

| 步骤 | 用哪个 | 理由 | temperature |
| --- | --- | --- | --- |
| 拆解（结构化） | `deepseek-chat` | 只要稳定 JSON | 0.3 |
| **差异化改写** | `deepseek-chat` | 质量决定客户是否通过，但 R1 输出不稳定，不用 | 0.8 |
| 改写重试（带失败原因） | `deepseek-chat` | 需要精确执行“第 3 句太像”这类指令 | 0.7 |
| 发布文案 | `deepseek-chat` | 短、便宜 | 1.0 |
| 质检打分（17 项中的文本项） | `deepseek-chat` | 每项独立打分，便宜 | 0 |
| 复杂结构分析（备用） | `deepseek-reasoner` | 仅当改写质量不达标时人工触发 | — |

> **不要默认上 R1**：贵 3–5 倍、慢、且它的思考过程会混进 JSON。只在“改写连续 2 次不达标”时作为兜底。

### 3.3 必须用的两个省钱手段

**① 前缀缓存（Context Caching）**

DeepSeek 会自动缓存**完全相同的请求前缀**。所以提示词顺序必须是：

```
[固定 system：角色 + 规则 + 输出格式 + few-shot]   ← 完全不变，命中缓存
[可变 user：原文 + 平台 + 字数 + 禁止事项]        ← 每次不同
```

如果把日期、项目名甚至随机 ID 塞在 system 里，缓存永远不命中，成本直接翻 4 倍。**这一条价值最大，也最容易写错。**

**② JSON 模式 + 服务端校验**

```json
{ "response_format": { "type": "json_object" } }
```

- JSON 模式要求 prompt 里**出现 “json” 字样**并能给出示例，否则可能返回空内容。
- 拿到结果后**必须用 zod/ajv 校验**，校验失败就带错误信息重试一次（这是最便宜的重试）。
- 不要用正则从自然语言里抠 JSON，那是返工之源。

### 3.4 改写提示词的工程约束

```
输出必须同时满足（按顺序校验，不满足即重写）：
1. 字数 ∈ [预算 × 0.9, 预算 × 1.1]        ← 先卡字数
2. claims.length === 1                     ← 再卡单承诺
3. 结构 4 项（钩子/案例/承诺/CTA）至少换 3 项
4. 无书面语（禁用词表）+ 平均句长 ≤ 14 字
```

关键设计：**校验在代码里做，不在提示词里做**。提示词只负责“写”，代码负责“判”。这样阈值可调、可回归测试、可灰度。

`spikes/deepseek-dryrun.mjs` 已经把这段校验跑通了，可以直接看“拦住 / 通过”的判定输出。

### 3.5 一个硬限制（会影响质检设计）

> **DeepSeek 对话接口不支持图片输入。**

所以第 8 步质检里这几项**不能**交给 DeepSeek：

- 封面可读性（字号/对比度在缩略图下是否可读）→ 规则计算（像素级）+ 可选多模态
- 画面是否出现禁用元素 → 多模态
- 字幕是否与画面错位 → 规则（时间戳比对）

处理方式：

| 质检项 | 实现 |
| --- | --- |
| 文本类（差异、钩子、承诺、口语感、CTA、合规词） | ✅ DeepSeek |
| 数值类（时长、字数、行宽、对比度、素材齐备） | ✅ 规则代码 |
| 视觉类（画面内容、封面观感） | ⚠️ 可选接多模态（同厂 doubao-vision 或 Qwen-VL），V1 先只做规则项 |

> V1 建议：视觉质检只做**能算的**（对比度、字数、安全区遮挡）。“好不好看”留给人，别硬上模型。

## 4. 即梦接入（火山引擎方舟）

### 4.1 形态

即梦的模型能力通过**火山引擎方舟（Ark）**开放，与豆包同源。三个能力对我们有用：

| 能力 | 用于 | 对应我们的步骤 |
| --- | --- | --- |
| 文生图 / 图生图（Seedream 系） | 产品图美化、封面底图、统一风格首帧 | 第 5、6 步 |
| 文生视频 / **图生视频**（Seedance 系） | B-roll、空镜、产品动态镜头 | 第 5 步 |
| 视觉理解（可选） | 画面质检 | 第 8 步（V2） |

### 4.2 调用形态

```
鉴权     Authorization: Bearer $ARK_API_KEY
图片     同步接口，一次请求直接返回图片 URL
视频     异步任务：POST 创建 → GET 轮询 → 拿 URL
轮询建议 3–5 秒一次
```

### 4.3 必须处理的三个工程点

1. **图片 URL 有时效**（通常 24 小时内）→ 拿到就下载进 MinIO，不要存 URL。
2. **视频异步任务的 `task_id` 要落库**，且轮询要能跨进程恢复（worker 重启后接着轮）。
3. **分辨率与画幅**：竖屏 9:16 要显式传，不要指望默认值。默认多是 1:1 或 16:9，直接用于抖音会裁切。

### 4.4 图生视频是我们的主力用法

因为口播视频需要**产品一致性**。文生视频每次都是新的“想象中的榨汁杯”，三个镜头三个杯子。

正确做法：

```
产品实拍图（用户上传）
   ↓ 即梦图生图：统一背景/光线/风格（可选）
   ↓ 作为首帧
即梦图生视频：生成 5s 动态镜头（倒水、旋转、开盖）
   ↓
下载 → 入素材库 → 交给 FFmpeg 拼接
```

这样每次都是**同一个杯子**在动。这是能不能用于商业交付的分水岭。

## 5. 可灵接入（Kling）

### 5.1 形态

```
鉴权     JWT（用 AccessKey + SecretKey 本地签发，HS256）
        Authorization: Bearer <jwt>
        payload: { iss: ak, exp: now+1800, nbf: now-5 }
端点     文生视频 / 图生视频 / 图片生成（各自独立）
轮询     GET <task endpoint>/{task_id}
模式     std（便宜快） / pro（质量好，贵）
时长     5s / 10s（没有更长）
```

### 5.2 与即梦的定位差异

| 维度 | 即梦（Seedance） | 可灵（Kling） |
| --- | --- | --- |
| 强项 | 与豆包同生态、图生图一致性好 | 运镜/物理运动更自然，图生视频口碑好 |
| 单段时长 | 5s / 10s | 5s / 10s |
| 鉴权复杂度 | 低（API Key） | 中（JWT 自签，注意时钟偏差） |
| 建议用途 | 产品图、封面底图、静态转动态 | **B-roll 主力**、运镜镜头 |
| 失败重试成本 | 中 | 中高 |

> 建议：**两个都接**，但按镜头类型路由——产品展示走即梦（一致性），氛围/运镜走可灵（运动自然）。这也顺便解决了单供应商故障问题。

### 5.3 两个坑

1. **JWT 的 `exp` 不能太长**（一般 30 分钟），且不要每秒重签——按任务批量复用，缓存到内存。注意服务器时钟同步，`nbf` 留 5 秒余量。
2. **同一条任务不要并发轮询**。多个 worker 同时轮同一个 task_id 会浪费配额，也可能触发风控。用 `select for update skip locked` 挑任务。

## 6. 镜头级生成策略（这是成本的核心）

### 6.1 时长数学

视频模型只出 5s / 10s 片段，而我们要 30s 成片：

| 方案 | 片段数 | 说明 |
| --- | --- | --- |
| 30s 全用 AI 视频 | 6 × 5s | ❌ 贵、且口型不对，不可用 |
| 口播 + 3 个 AI B-roll | 3 × 5s | ✅ **推荐** |
| 口播 + 1 个 AI 片头 | 1 × 5s | ✅ 最省 |
| 全图片（无 AI 视频） | 0 | ✅ 默认路线 |

### 6.2 推荐的分镜配比（30 秒）

```
0–3s    钩子      口播画面（图片/数字人）
3–8s    痛点特写  即梦图生视频（产品细节）      ← AI 1
8–14s   展示      用户产品图（静态推拉）
14–20s  使用场景  可灵图生视频（倒水/出汁）    ← AI 2
20–26s  参数      文字卡 + 产品图
26–29s  CTA       文字卡
```

**AI 只占 10s / 29s，成本可控在个位数。**

### 6.3 每镜的生成契约

```json
{
  "shot_id": "s02",
  "provider": "jimeng",
  "mode": "image2video",
  "first_frame": "artifact://prod-shot-b",   // 必须是已确认的产品图
  "prompt": "水从杯口冲下，泡沫带走果渣，微距，浅景深，暖光，镜头轻微推进",
  "negative_prompt": "文字, 水印, 畸变的手, 多余杯体, 品牌logo变形",
  "ratio": "9:16",
  "duration_sec": 5,
  "cfg": 0.5,
  "seed": 20261120                         // 固定 seed 便于复现
}
```

四个字段必须坚持：**`first_frame`（一致性）、`negative_prompt`（少返工）、`seed`（可复现）、`duration`（控成本）**。

## 7. 成本与预算熔断

### 7.1 量级对比（同一单 30s）

| 路线 | 模型调用 | 成本量级 | 耗时 |
| --- | --- | --- | --- |
| 纯配音 + 图片 | DeepSeek + TTS | **¥0.1–0.3** | 1–3 min |
| + 1 个 AI 镜头 | 上述 + 1 次视频 | **¥1–4** | +2–5 min |
| + 3 个 AI 镜头 | 上述 + 3 次视频 | **¥3–12** | +6–15 min |
| 数字人 30s | 上述 + 数字人 | **+¥3–15** | +5–30 min |

> 视频模型的单价跨度很大（std 与 pro 差 3–5 倍，5s 与 10s 差一倍）。**上表只用于排序，实际按控制台价目算。**

### 7.2 三道闸门（缺一不可）

```
① 提交前估算     estimateCost() 先算，超单镜预算直接拦
② 项目级熔断     单项目累计超过阈值（如 ¥15）→ 停止一切 AI 生成，转图片路线
③ 日级熔断       当日总消耗超阈值 → 全局停，发通知
```

实现要点：`estimateCost` 在**点击生成前**就要显示在按钮上（“生成本镜头 ≈ ¥1.20”）。让用户明确知道每一次点击在花钱。

### 7.3 `provider_calls` 必须记的字段

```
provider, model, kind, units, unit_name, unit_price,
cost, latency_ms, attempt, org_id, project_id, shot_id, cached_hit
```

有了这些，SaaS 化时的计费、毛利分析、供应商比价都是现成的。

## 8. 降级链（保证永远能出片）

```
首选：即梦 image2video（5s，产品一致）
  ↓ 审核拦截 / 余额不足 / 超时 / 失败 2 次
备选：可灵 image2video（同首帧，std 模式）
  ↓ 仍失败
降级：静态图 + Ken Burns 推拉（FFmpeg 本地，零成本）
  ↓ 仍不可用（无图）
兜底：品牌色文字卡（模板生成）
```

**关键：AI 视频永远是“锦上添花”，不是“雪中送炭”。** 任何 AI 生成失败都不应该让成片出不来——这是工作室能不能日更的底线。

## 9. 合规

1. **内容审核是双层的**：供应商侧会拦截（政治/暴恐/色情/侵权），我们侧也要拦（绝对化用语、医疗承诺、竞品名）。供应商通过 ≠ 平台通过。
2. **AI 生成标识**：即梦/可灵输出可能带水印或元数据标识，但**不能依赖**。我们自己在渲染层加角标 + 写文件元数据，并作为质检项。
3. **肖像/商标**：用户上传的产品图与人物图要勾选授权声明；生成提示词里禁止出现真实明星、他人品牌 logo（写进 `negative_prompt` + 服务端校验）。
4. **DeepSeek 内容安全**：改写环节的“禁止事项”要作为硬约束入 prompt，并在质检项里复查（模型会忘）。

## 10. 开工前的核对清单（务必先做，10 分钟）

| 项 | 要确认什么 | 影响 |
| --- | --- | --- |
| DeepSeek 模型名与价格 | `deepseek-chat` / `deepseek-reasoner` 当前单价、缓存命中价 | 成本模型、缓存策略 |
| 即梦 | Ark 上图片/视频的**确切模型 ID**、是否已开通、是否支持图生视频 | 可能整个 B-roll 方案要调整 |
| 即梦 | 视频异步任务的**轮询端点与状态字段**、产物 URL 有效期 | 下载策略 |
| 可灵 | API 是否需要**企业认证**、单账号并发上限 | 能否当天开工 |
| 可灵 | 图生视频是否支持“首帧 + 尾帧”、`cfg` 取值范围 | 镜头可控性 |
| 双方 | 是否支持**固定 seed**、是否返回水印 | 一致性与合规 |
| 双方 | 内容审核的**拒绝返回码**（用于区分“可重试”与“不可重试”） | 降级链是否可靠 |

第 3 个（DeepSeek 改写）尤其重要：**如果 JSON 合法率低于 95%，整个改写流水线要改成“带校验的重试循环”**，这是架构级的决定。

## 12. 需要你决定的三件事

1. **B-roll 的默认条数**：0（最省）/ 1（片头）/ 3（推荐）？这决定默认成本锚点。
2. **谁做 B-roll 主力**：即梦（一致性优先）还是可灵（运动优先）？建议先各跑 spike 再定。
3. **视觉质检要不要上多模态**：V1 只做规则可算项，还是直接接一个视觉模型（doubao-vision / Qwen-VL）？
