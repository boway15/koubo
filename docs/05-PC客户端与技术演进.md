# PC 客户端演进 · 两个决策已锁定

> 补充 `04`。本文回答两个问题：**① 已定的两个小决策怎么落地；② 期望的 PC 客户端会对现在的架构提出什么硬约束——哪些必须现在做，哪些不能提前做。**

---

## 1. 两个决策已锁定

| 项 | 结论 | 工程含义 |
| --- | --- | --- |
| 多样性默认策略 | **分给不同厂商**（每镜一家） | `route(diverse)` 为默认值；`sampleCount = 1`；同单 3 镜尽量不同 provider |
| 中转是否在交付物里标注 | **可以标注** | `publish-notes.md` 与 `manifest.json` 增加「生成来源」字段 |

### 1.1 多样性 = 分给不同厂商，需要注意什么

默认「每镜一家」省钱又快，但有一个副作用必须处理：**三家生成的色调、质感、锐度不一致**。

三道约束：

```
① 同一单共用一套 prompt 风格前缀（光影 / 镜头 / 色温词汇固定）
② 所有 B-roll 生成后过一遍统一 LUT（FFmpeg，一次调用，几乎零成本）
③ 质检项 12 里加一条：镜头间色调偏差 > 阈值 → warn
```

> 第 ③ 条容易被忽略。3 个镜头来自 3 家，单看每一帧都合格，连起来像三个片子。这是客户最能一眼看出“AI 拼的”的地方。

### 1.2 交付物标注的具体形式

在 `manifest.json` 里加一段，**不进入成片画面**：

```json
{
  "generation_sources": [
    { "shot": "02", "kind": "video", "provider": "jimeng", "relay": false },
    { "shot": "04", "kind": "video", "provider": "kling",  "relay": false },
    { "shot": "06", "kind": "video", "provider": "hailuo", "relay": false },
    { "shot": "03", "kind": "image", "provider": "jimeng", "relay": false }
  ],
  "relay_used": false
}
```

若走过中转：`"relay": true, "relay_provider": "kie", "upstream_model": "veo3"`。

规矩：**标注在文件里，不上画面**。画面上的标识是「AI 生成」角标（合规要求），与供应商无关。

## 2. 一句话结论：PC 客户端不是“再做个 UI”，而是“多一个执行器”

很多人把桌面端理解成“把网页包起来”。对我们这套系统，这个理解会错失最大的价值。

真正的价值在这里：

```
系统里最贵、最耗 CPU/GPU 的两件事：
  ① ASR（视频上传后的识别）
  ② 渲染（FFmpeg 拼接 30s 成片）

这两件事恰好都能在用户的 PC 上跑完。
```

**结果：桌面端把服务器最重的两个负载吸走了。** 服务端只剩「调 LLM/TTS/视频模型 + 存文件 + 发交付链接」。

对 SaaS 化的意义更大：**渲染在本地 = 边际成本近零**，这是定价上的结构性优势。

## 3. 五个现在就必须遵守的硬约束

这五条如果现在不做，以后加桌面端要重写。都不是大事，但都不可逆。

### 3.1 后端必须是纯 HTTP 服务，不能依赖浏览器会话

| 现在就这样做 | 不要这样做 |
| --- | --- |
| `Authorization: Bearer <token>` | Cookie + Session（桌面端没有） |
| 所有接口返回 JSON / SSE | Next.js Server Actions 写业务 |
| 长任务返回 `job_id`，进度走 SSE | 依赖页面内状态驱动 |
| CORS 允许 `http://localhost:*` / `tauri://localhost` | 同源假设 |

> 实践：**Web 工作台就是“第一个客户端”**，它和未来的 PC 客户端调同一套 API。这件事本身就是验收标准：如果 Web 端能只靠 API 跑起来，桌面端就能接。

### 3.2 时间线必须是数据，不是代码 ← 最重要的一条

因为要支持「服务端渲染」和「本地渲染」两种执行方式，渲染输入必须是一个**两端都能解释的 JSON**：

```json
{
  "version": 1,
  "canvas": { "w": 1080, "h": 1920, "fps": 30 },
  "tracks": [
    { "type": "voice",  "src": "artifact://a1", "startMs": 0 },
    { "type": "bgm",    "src": "artifact://a2", "duckDb": -12 },
    { "type": "video",  "src": "artifact://a3", "in": 0, "out": 5000, "atMs": 3200, "fit": "cover" },
    { "type": "image",  "src": "artifact://a4", "atMs": 8000, "durMs": 6000, "motion": "kenburns" },
    { "type": "text",   "src": "artifact://a5", "styleId": "subtitle-bold-64" }
  ],
  "overlays": [{ "type": "aiBadge", "pos": "top-right" }],
  "lut": "artifact://lut-01"
}
```

为什么必须现在定：

- 如果渲染逻辑写成“服务端代码”，桌面端就只能调用远程渲染，白浪费用户 GPU。
- 如果时间线是数据，**本地渲染器只是同一个 spec 的另一个实现**，甚至可以第一版先用服务端，桌面端上线时再实现本地渲染器，业务代码不动。

> 一句话：**渲染器是可替换的，时间线是契约。** 这和前面“供应商是可替换的，能力是契约”是同一个思路。

### 3.3 存储要抽象成接口，不能到处写路径

```ts
interface Storage {
  put(key: string, data: Buffer | Stream, mime: string): Promise<string>
  get(key: string): Promise<Stream>
  url(key: string, ttlSec: number): Promise<string>
}

// 服务端：MinIO/S3     桌面端：file:// 本地目录
```

桌面端要的是**本地缓存与离线草稿**，所以 key 必须与物理位置解耦。现在所有 key 用 `{org_id}/{project_id}/{artifact_id}`，两边都能映射。

### 3.4 任务要带 `runner` 概念

```sql
-- jobs 表加一列
runner text not null default 'server'   -- server | desktop
```

含义：同一套 `jobs` 模型，桌面端可以领取 `runner=desktop` 的任务（ASR、渲染），服务端只做轻任务（LLM、TTS、生成、质检）。

配套两件事：

1. **桌面端要能上报结果**：`POST /jobs/:id/complete`（带 artifact 上传）。
2. **桌面端要能心跳**：否则任务卡在“已分配”状态下永远不回收。

> 别把它做成“两套系统”。它就是一个队列，两类消费者。

### 3.5 认证要预留“换令牌”的口子

| 阶段 | 认证 |
| --- | --- |
| V1 本机 | 单个 `LOCAL_TOKEN`（环境变量，启动即注入） |
| SaaS | OAuth / 邮箱验证码 → JWT，桌面端用 **PKCE** 授权码流程 |

现在只要做到：**所有请求都过一层 `getAuth(req)`**，不要在业务代码里直接读环境变量。桌面端上线时改成从钥匙串读 token 即可。

## 4. 桌面端到底多了哪些能力

按价值排序，不是按实现难度：

| 能力 | 为什么值钱 |
| --- | --- |
| **本地 ASR + 本地渲染** | 服务器零成本，用户 GPU 免费。这是省钱核心 |
| **拖拽整包素材** | 工作室的素材在本地文件夹，上传 20 张图不要一个个点 |
| **夜间队列** | 下班前排 10 单，第二天拿成品。浏览器标签会被关，桌面端不会 |
| **大文件无限制** | 浏览器 200MB 上传上限不存在了，直接读本地文件 |
| **离线草稿** | 断网也能改文案、调分镜，联网后同步 |
| **系统级通知** | 跑完一条弹通知，不用盯页面 |

反过来，**PC 客户端不该做的事**：

- ❌ 不存交付链接（客户链接必须由服务端签发，客户端不能当主机）
- ❌ 不存供应商 key（key 在服务端，避免泄露与轮换困难）
- ❌ 不做权限判断（服务端为准，客户端只是展示）

## 5. Tauri 还是 Electron：现在不用选，但要留口

| | Tauri 2 | Electron |
| --- | --- | --- |
| 安装包 | ~10MB | ~100MB+ |
| 内存 | 低（用系统 WebView） | 高（自带 Chromium） |
| 原生能力 | Rust + sidecar | Node 直接集成 |
| 适合 | 小工具型、分发量大 | JS 团队、插件多 |
| 本地跑 FFmpeg | sidecar 机制干净 | child_process 直接调 |
| 学习成本 | 要碰一点 Rust | 基本没有 |

**建议：先不选。** 现在只需要保证后端 API-first + 时间线是数据，两者都能接。真正要选的时候看两条判据：

1. 团队里有没有人能改 Rust（没有 → Electron）
2. 是否需要大量本地文件/系统级集成（重度 → Tauri sidecar 更干净）

> 你现在的环境是 Windows，Windows 上两者都稳（WebView2 就是 Chromium）。**优先 Windows 发布**，Mac 后期再说。

### 5.1 分发上躲不开的四件事

后期做桌面端，这四件一定会撞上，提前知道可以少踩：

| 项 | 现实 |
| --- | --- |
| **代码签名** | Windows 不签名会被 SmartScreen 拦截。证书要提前申请（个人/企业流程不同） |
| **自动更新** | 必须自己做（Tauri updater / electron-updater），且要和版本号策略配合 |
| **FFmpeg 打包** | 要随包分发二进制，注意 LGPL/GPL 差异（libass 属 GPL 分支，商用要评估） |
| **模型文件** | 本地 ASR 的 whisper 权重几百 MB，首次启动下载还是随包？随包会让安装包爆掉 |

> 最后一条最容易忽略：`large-v3` 权重约 3GB。**桌面端建议用 small/medium 或按需下载**，精度差一点但用户体验好很多。

## 6. 现在不该做的事

明确列出来，避免提前复杂化：

| 不要做 | 原因 |
| --- | --- |
| ❌ 现在就写桌面端 | 主链路还没跑通，做了也是返工 |
| ❌ 现在就做 Tauri/Electron 技术选型 | 约束已留好，晚选反而更准 |
| ❌ 现在就做离线同步/冲突解决 | 离线草稿是二期，先把在线路径跑顺 |
| ❌ 现在就把渲染拆成独立渲染器进程 | 服务端先用一个 FFmpeg 函数，spec 定好即可 |
| ❌ 现在就上多端 token/设备管理 | 单机 `LOCAL_TOKEN` 够用 |

## 7. 里程碑调整

| 阶段 | 内容 | 变化 |
| --- | --- | --- |
| Spike | 模型能力验证 | 不变 |
| **M0 骨架** | + **时间线 spec 定义** + `jobs.runner` 列 + `Storage` 接口 | **+0.5 天** |
| M1 主链路 | 不变（渲染先只做服务端实现） | — |
| M2 质检与交付端 | + 质检项 12 增“镜头间色调偏差” | +0.5 天 |
| **M3 桌面端** | Tauri/Electron 壳 + 本地 ASR + 本地渲染器 | 新增，约 2–3 周 |

**关键：M0 那 0.5 天是唯一必须现在付的代价。** 付了这半天，桌面端随时可以接；不付，以后要重写渲染与任务层。

## 8. 验收：怎么知道自己没跑偏

三条自检，都能当场验证：

1. **API 自检**：把 Web 工作台用 `curl` 重放一遍核心流程（建项目 → 上传 → 跑 → 导出）。能跑通说明 API-first 成立。
2. **渲染自检**：把 `timeline.json` 存下来，换一台机器、用同一个 ffmpeg 命令能渲染出**逐帧一致**的成片。能做到说明 spec 完整、没有隐式状态。
3. **任务自检**：把 `runner` 手动改成 `desktop`，任务应当停在“已分配”并等心跳超时回收。能做到说明队列模型没写死。

---

## 9. 一句话总结

> **PC 客户端不是未来的 UI，是未来的执行器。**
> 现在只需要做一件事：让“怎么执行”变成数据（时间线 spec + runner 字段 + 存储接口），而不是代码。
