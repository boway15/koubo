# 业务适配分析：知识主播口播 与 采访类视频

> 直接回答：**知识主播——合适，但要改 4 处；采访——现在的架构不合适，需要第二条管线。** 两者可复用约 60% 基础设施。
>
> 但有个好消息：**这两类在你的场景里会长成同一个东西**——主播旁白 + 采访原声。那是 V2 的商业方向，不是两个产品。

---

## 1. 结论先行

| 业务形态 | 适配度 | 结论 |
| --- | --- | --- |
| **知识主播口播**（单人、讲透一个点） | ✅ **85%** | 主链路直接可用，改 4 处即达标 |
| **知识系列**（一题拆 3–5 条） | ✅ **80%** | 需加「选题拆分 + 系列共享视觉」 |
| **纯口播访谈**（一人说、一人剪） | ⚠️ **35%** | 缺说话人分离与选句能力 |
| **采访成片**（多人、原声拼接） | ❌ **30%** | **需第二条管线**（素材驱动，不是生成驱动） |
| **解说 + 采访原声**（最强商业形态） | 🟡 **50%（V2）** | 两条管线合流，价值最高 |

---

## 2. 为什么知识主播合适

它和现有设计的契合点是结构性的：

| 现有设计 | 知识主播要的 | 契合 |
| --- | --- | --- |
| 一条视频一个承诺 | 一条讲透一个点 | ✅ 完全一致 |
| 差异化改写 | 避免搬运同行观点 | ✅ 一致（且更刚需） |
| 按句切字幕 | 知识类全靠字幕吸收信息 | ✅ 甚至更重要 |
| 配音 + 图片路线 | 知识主播常不愿出镜 / 要批量 | ✅ 一致 |
| 模板剪辑 | 需要稳定的视觉规范 | ✅ 一致 |

**一句话：知识主播就是这套系统最初设计的那类用户。**

---

## 3. 但要改这 4 处（不改会直接做废）

### 3.1 时长：15–30s 是错的

知识类真实时长是 **60s / 90s / 180s**。按 4 字/秒：

| 时长 | 字数 | 字幕条数 | 镜头数（每 6–10s 一变） |
| --- | --- | --- | --- |
| 60s | ~240 | ~20 | 6–10 |
| 90s | ~360 | ~30 | 9–15 |
| 180s | ~720 | ~60 | 18–30 |

**连带影响三件：**

1. **B-roll 3 条不够**。180s 需要 18–30 个视觉变化，不可能全用 AI 视频（成本爆）。
2. **TTS 要分段合成**（见 3.4）。
3. **质检的「时长匹配平台」区间表要改**。

### 3.2 “单承诺”约束要改成“单主题 + 三点”

知识类不能用「一个承诺」约束（那是带货话术），否则会写成“一句话口号”，信息量不够。

```
旧：claims.length === 1
新：topics.length === 1  ∧  points.length ∈ [2, 4]
     points 之间不能互相包含（不能把同一点拆成三条）
```

### 3.3 最大的新风险：事实失真（不是同质化）

带货写错了顶多夸大，**知识写错了是事故**。而改写环节正是引入错误的地方：

| 失效模式 | 例子 | 后果 |
| --- | --- | --- |
| 数值改错 | “下降了 30%” → “下降了 50%” | 严重 |
| 术语替换 | “光合作用” → “光能转化” | 不专业 |
| 张冠李戴 | 把 A 的研究说成 B 的 | 严重 |
| 因果关系加强 | “相关” → “导致” | 学术不严谨 |
| 补充了原文没有的“常识” | 模型自己“补全”了论据 | **最隐蔽、最难查** |

**必须新增质检项（15–17）：**

| # | 检查 | 方法 |
| --- | --- | --- |
| 15 | **数值与术语保真** | 抽取改写稿中所有数字/专有名词，逐个回原文核对；未在原文出现的**数字**直接 fail |
| 16 | **事实可溯源** | 每个论断需能对应到原文某句；无出处的断言标 warn |
| 17 | **无自行补充** | 对比原文与改写稿的“信息点集合”，新增信息点且无来源 → fail |

> 第 17 项是知识类的命门。**“模型很聪明地帮你补了一条论据”，在知识领域是灾难。** 这也是为什么第 3 步不能是“让模型写”，而必须是“让模型重组已确认的信息”。

### 3.4 TTS 长文本必须分段

3 分钟一口气合成会出现：韵律漂移、气息不自然、越到后面越像念稿。

```
按段落（200–400 字）分段合成
→ 每段独立取字级时间戳
→ 拼接时插入 200–400ms 句间停顿
→ 整轨做一次响度归一（-14 LUFS）
```

**这对时间线 spec 有影响**：`voice` 轨道不能是单个文件，必须是**分段数组**。

```json
{ "type": "voice", "segments": [
  { "src": "artifact://v1", "startMs": 0 },
  { "src": "artifact://v2", "startMs": 18400, "gapMs": 320 },
  { "src": "artifact://v3", "startMs": 41200, "gapMs": 260 }
]}
```

> 这一条现在改很便宜（改个 spec），上线后改要重渲所有片子。

### 3.5 视觉：知识类靠信息图形，不靠 B-roll

这是最容易做错的地方。180s 的知识视频，如果只有“图片推拉 + 3 个 AI 镜头”，观众 40 秒就划走。

真实的视觉配比：

```
字卡 / 关键词卡      30%   ← 模板生成，零成本
图表 / 数据可视化    25%   ← 模板生成，需数据输入
原文/资料截图        20%   ← 用户上传
产品/实拍素材        15%   ← 用户上传，可 Ken Burns
AI 生成镜头          10%   ← 即梦/可灵，只用在“无法实拍”处
```

**结论：模板系统的重心从“视频模板”转向“信息图卡片模板”。** 这比接更多视频模型重要得多。

## 4. 为什么采访类不合适

不是“差一点”，是**核心操作相反**。

### 4.1 两条管线的核心动作根本不同

```
口播（生成驱动）          采访（素材驱动）
──────────────           ──────────────
改写文字  → 生成画面      转录原片 → 挑选句段
“写出来”                   “剪出来”
```

| 步骤 | 口播管线 | 采访管线 |
| --- | --- | --- |
| 进料 | 主题 / 文案 / 视频 | **多段长素材（1–3 小时）** |
| 转录 | ASR 得文字 | ASR + **说话人分离（diarization）** |
| 核心处理 | **改写**（拉开差异） | **选句 + 排序**（保真，禁止改写） |
| 画面 | 生成 / 图片 | **原片时间码剪辑**（不生成） |
| 时长控制 | 字数预算 | **删口头语与停顿** |
| 质量判据 | 差异度 | **引用准确性**（不能断章取义） |

> **最关键的一条：采访里的“改写”是禁止的。** 你不能改别人说过的话。所以整个第 3 步在采访管线里不存在，取而代之的是 `selects`（选段清单，带原片时间码）。

### 4.2 缺的技术能力（现在完全没有）

| 能力 | 为什么必须 | 现状 |
| --- | --- | --- |
| **说话人分离** | 不知道谁说的，就无法做多人字幕、无法归类观点 | ❌ 无 |
| **话题分段** | 1 小时素材要切成可检索的段落 | ❌ 无 |
| **金句/观点抽取** | 选句的依据 | ❌ 无 |
| **叙事重组** | 把散落的回答拼成有逻辑的片子 | ❌ 无 |
| **长素材管理** | 1 小时视频的文件、转写、检索 | ⚠️ 只支持 ≤5 分钟 |
| **删口头语/停顿** | 采访剪辑 70% 的工作量在这里 | ❌ 无 |
| **多机位同步** | 真实采访多为 A/B 机 | ❌ 无 |

### 4.3 一个好消息：渲染层可以直接复用

时间线 spec 里 `{ src, in, out, atMs }` 这种写法，**本来就能引用原片时间码**（当初是为 AI 片段设计的，歪打正着）。

```json
{ "type": "video", "src": "artifact://raw-interview-01",
  "in": 128400, "out": 134900, "atMs": 3200, "fit": "cover" }
```

所以：**渲染器、字幕、封面、质检框架、交付端、时间线契约——这 60% 不用重做。** 要新建的只是前段（转录增强 + 选句 + 重组）。

## 5. 现在必须做的 5 个小改动（总计约 1 天）

这些不做，V2 要么重写，要么要重跑所有历史数据：

| # | 改动 | 代价 | 不做的后果 |
| --- | --- | --- | --- |
| 1 | `projects.mode` 枚举：`script` \| `edit` | 1 行字段 | 数据模型写死单管线 |
| 2 | `transcripts.segments_json` 每段加 **`speaker`** 字段 | 字段 | **V2 要重跑所有转录**（最贵） |
| 3 | `voice` 轨道改成 **分段数组** | 改 spec | 长文本 TTS 无法分段，知识视频做不了 |
| 4 | `artifacts.kind` 由**管线模板**定义，不写死 8 件 | 设计 | 采访 8 件交付物完全不同 |
| 5 | 字幕样式支持 **speaker → style** 映射 | 字段 | 多人字幕做不了 |

> 第 2 条最贵。ASR 转一次 1 小时素材要钱要时间，如果当时没存 speaker，以后补不回来。**哪怕 V1 只有一个人说话，也要存 `speaker: "spk_0"`。**

## 6. 两条管线如何共存

```
                    ┌─────────────────────────┐
                    │  共用层（60%）          │
                    │  产物DAG / 时间线 / 渲染 │
                    │  质检框架 / 交付端 / 模板 │
                    └───────────┬─────────────┘
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
   ┌──────────▼──────────┐            ┌───────────▼───────────┐
   │ script 管线（V1）    │            │ edit 管线（V2）        │
   │ 主题/文案 → 改写     │            │ 长素材 → 转录+Diarize │
   │ → 生成/图片         │            │ → 选句 → 重组         │
   └─────────────────────┘            └───────────────────────┘
```

实现方式：**管线模板（`pipelines` 表）**，每行定义自己的步骤序列与交付物清单。`projects.mode` 选模板，业务代码不写 if/else。

这和「供应商是一张表，不是 if/else」是同一个思路。

## 7. 商业上最值钱的方向（提前说，但别现在做）

**解说 + 采访原声** = 知识类纪录短片。这是采访类内容的真实变现形态，也是你这两个需求真正的合流点：

```
主播旁白（TTS，可控、可改）   ┐
                              ├─→ 同一条时间线
采访原声（真人，不可改）      ┘
+ 资料画面 / 图表 / 字卡
```

这条路径上：

- 旁白部分用 `script` 管线（可改写、可控时长）
- 采访部分用 `edit` 管线（保真、原声）
- **两条管线产出接入同一个时间线 spec** → 渲染层完全复用

所以现在的架构不需要为了它改什么，只要把第 5 节的 5 个字段留好。

## 8. 排期建议

| 阶段 | 内容 | 服务谁 |
| --- | --- | --- |
| **V1（现在）** | script 管线 + 知识主播 4 处改造 + 5 个字段预留 | 知识主播 |
| V1.5 | 信息图卡片模板库 + 系列化 | 知识系列 |
| V2 | edit 管线：diarization + 选句 + 重组 | 采访 |
| V2.5 | 两条管线合流（解说+原声） | 知识纪录短片 |

**理由：** 知识主播离现有设计只有 4 步之遥，能最快交付真实客户；采访要新建半条管线（diarization + 选句 + 重组），现在做会拖垮主链路。

---

## 9. 一句话总结

> **知识主播：改 4 处（时长 / 单主题三点 / 事实质检 / TTS 分段），就能用。**
> **采访：不是不行，是另一条管线——60% 复用，前段要重做。**
> **现在只需付 1 天代价：5 个字段。尤其是转录存 `speaker`，不存以后补不回来。**
